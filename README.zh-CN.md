# CCG WorkPanel

面向快消行业的共享业务数据工作台

**让分散的快消业务数据能够被共同理解与复用。**

## 为什么做这个项目？

快消企业每天都在产生大量数据。

销售、库存、客户、商品、来货、预测和订货，这些信息分散在 ERP、Excel
和不同部门使用的业务工具中。实际工作中遇到的一个问题是：数据并不是没有，
而是很难放在一起使用。

同一个客户，在不同系统中可能有不同的名称和编码；同一款产品可能对应多个
包装规格和 SKU；各部门对于渠道、商品分类和数据统计口径，也可能有不同的理解。

每当我们想做一张新报表，或者开发一个新的业务工具，就不得不重新整理这些
基础资料、确认对应关系。

**CCG WorkPanel 想尝试解决的，就是如何让这些分散的数据能够被共同理解和反复使用。**

## CCG WorkPanel 是什么？

CCG WorkPanel 是一个以主数据管理（MDM）为基础的开源业务数据工作台。

它尝试为客户、商品、SKU、渠道等基础业务对象建立统一定义，通过数据映射
和明确的数据契约，让不同来源的数据能够关联，并供销售、库存、预测、订货等
业务模块共同使用。

我们的目标不是替代 ERP，也不是要求不同部门放弃现有工具，而是在已有数据
来源与业务应用之间建立一层可以复用的数据基础。

考虑到企业生产系统的安全性与访问权限，当前公开版本先采用文件导入与隔离的
本地数据库来验证这一思路，并提供完全虚构、从零生成的数据供使用者体验。
文件导入让使用者能检查具体记录、确认对应关系，也便于重复验证数据处理规则。

这是一个持续探索中的开源项目，而不是一套开箱即用的完整 ERP 或 S&OP 系统。

## 目前能做什么？

目前的公开版本可以维护共同的基础资料、查看销售实绩，并围绕库存、来货和
人工预测开展订货分析。下表区分可通过浏览器使用的功能，以及已经具备处理逻辑、
但仍需通过程序调用的服务核心。

| 应用 | 业务用途 | 当前公开版本的支持形式 |
| --- | --- | --- |
| MDM 与 Import Center（主数据与导入中心） | 建立共同的客户、Product、SKU 和基础资料 | 浏览器与 API：维护主数据，检查客户／产品／SKU／组合商品文件，审核后提交 |
| Sales Actual（ACT Sales，销售实绩） | 查看实际销售数量及产品、渠道、销售员等维度 | 浏览器与 API：销售文件映射、预览、发布和数量看板 |
| Inventory 与 Incoming（库存与来货） | 为计划提供期初库存、可用仓库和来货快照 | 文件解析与提交已有服务核心，Demo 初始化使用这些服务；尚无完整浏览器导入流程 |
| Forecast（人工预测） | 按渠道、产品填写四个月的销售预测 | 浏览器与 API：查看计划、选择来源、编辑并保存预测版本 |
| Ordering（订货） | 比较库存、来货和预测，查看最终订货 | 工作台展示四个月库存推演及最终订货状态；订货写入、确认、修订历史和计划周期锁定已有服务核心，尚无完整浏览器操作流程 |
| Portal、账号与权限 | 按岗位开放查看、编辑与账号管理 | 浏览器与 API：按权限展示入口，设置模块查看／编辑权限和管理账号 |

这些应用共用 MDM 中的客户、产品和渠道定义，但各自的数据处理规则与版本仍有区别。
**ACT Sales 看板发布不会自动成为 Ordering 的销售来源。**
Ordering 当前另有销售实绩文件导入服务；计划使用哪些数据，需要在计划周期中明确选择，
具体规则见下节。

## 数据如何被共同理解？—— MDM、映射与数据契约

要把不同来源的数据放在一起，首先需要确认它们描述的是哪个业务对象，
再确认数量和期间是否使用相同口径。MDM（主数据管理）为这些判断提供共同基础。

客户（Customer）可能在销售台账中使用门店简称，在财务资料中使用结算主体全称，
也可能因系统独立建档而拥有不同编码。但这些差异有时代表真正不同的门店、法人
或结算关系，不能仅凭名称相似就合并。

商品也有不同层次：**Product（产品）**用于组织相关商品并汇总业务信息；
**SKU（具体商品项）**代表需要单独识别的规格、包装或物料编码。
多个 SKU 可以关联同一个 Product，但它们的编码、数量和包装关系仍需分别保留。

MDM 维护这些对象，以及渠道、销售员和相关基础资料。销售可以沿用客户所属渠道，
库存和来货可以沿用产品目录，预测与订货可以使用相同的产品及渠道标识，
减少各模块重复整理基础资料的工作。

**数据统一不要求强制修改来源系统。** 原有工具可以继续保留自己的名称和编码。
导入工作台时，文件需符合当前导入器的格式和规则，并记录数据对应关系及检查结果。

下面的客户与商品关系完全虚构、从零构造。**这是设计理念示例，不代表当前所有导入器
支持任意来源编码和别名映射。** 这些记录也不是内置 Demo 数据。

| 虚构来源记录 | 确认后的共享业务关系 |
| --- | --- |
| 台账 A：`A-CUST-07`，月芽商店；台账 B：`B-CUST-42`，月芽商贸（示例） | 业务人员确认是同一客户后，可建立到共享客户 `CUS-EXAMPLE-01` 的来源映射；若是不同门店或结算主体，则应分别建档 |
| `SKU-EXAMPLE-01`：星谷麦片 300g；`SKU-EXAMPLE-02`：星谷麦片 600g | 两个独立 SKU 关联 Product `PRD-EXAMPLE-01`：星谷麦片；实际汇总遵守导入数量及包装契约，不擅自换算单位 |

数据契约就是各模块共同遵守的数据使用规则：文件需要哪些列，数量代表什么，
SKU 如何关联 Product，数据覆盖哪个期间，哪些仓库可以用于计划，以及什么条件下
可以提交或发布。销售数量不能用库存出库数量替代；“未填写”与“明确为零”也不同。

当前实现保留以下具体约束：

- **对应关系：** 数据模型包含外部编码映射与别名记录，MDM 导入引擎会读取这些记录，但未提供通用映射管理界面。当前 Sales 按 SKU 编码及确定性规范化规则识别商品，客户按规范化名称唯一匹配已保存的 MDM 记录，不做模糊业务实体猜测。
- **导入与发布：** 主数据导入采用整批提交，避免只写入半批结果。Sales 保留带符号原始数量，仅符合规则的正数量行进入发布事实。
- **计划与历史：** Planning Cycle（计划周期）需要明确采用销售／库存来源版本、来货快照及预测版本；新文件不能悄悄替换已选数据。预测以不可变版本保存，调整时生成新版本；锁定周期保留历史记录。

公开版本目前没有通用 ERP API 连接器。接入企业生产接口需要经过授权，并明确来源接口
约定和运行保障。更详细的文件格式与处理规则见[导入约定](docs/import-contracts.md)。

## 一个典型业务流程

1. **建立共同基础：** 确认客户、渠道以及 Product 与 SKU 的关系，通过 MDM 与导入中心校验并审核主数据。
2. **核对销售实绩：** 上传符合当前适配器约定的虚构销售文件，检查映射与预览，再发布数量看板。
3. **准备计划来源：** 用现有服务导入计划所需的销售实绩、库存和来货。内置 Demo seed 已为体验准备这些来源；浏览器尚不能完成全部导入。
4. **选择版本并填写预测：** 在订货工作台明确选择计划采用的数据版本，按渠道和产品填写四个月的人工预测，查看“期初库存 + 来货 − 预测”的预计月末库存。
5. **保留决策历史：** 服务核心支持人工最终订货、确认、修订历史和周期锁定；这些操作可通过合成 Demo 与测试了解，尚不是完整浏览器流程。

该流程用于理解数据如何协作，不会自动向 ERP 下单，也不提供自动需求预测。

## 体验本地 Demo

### Docker Quick Start

需要安装 Docker 和 Compose。请在仓库根目录执行：

```sh
docker compose -p ccgtools-open-demo -f deploy/local/compose.yml up --build -d --wait
```

启动后访问 <http://127.0.0.1:18080/login>。
独立 MySQL 服务仅绑定 `127.0.0.1:13306`，用于本地测试。

首次初始化按以下顺序执行：

1. 根据公开 Alembic 基线创建 MySQL 业务库结构。
2. 创建 SQLite 账号库结构。
3. 执行账号权限迁移，并核对迁移标记。
4. 写入合成演示账号及最终权限，再写入合成业务数据。
5. 启动应用。

应用启动和登录时会再次核对已执行的账号迁移，不会重置既有权限。
无需手动修改 SQLite。应用、数据初始化和数据库迁移使用同一个本地构建镜像。

可覆盖的环境变量见 [`.env.example`](deploy/local/.env.example)。
Compose 读取主机环境变量，不会自动加载这个示例文件。
其他本地开发方式见[本地开发说明](docs/local-development.md)。

### 合成演示数据

执行 `python3 -m demo.generate_data`，可重复生成 XLSX、CSV 和 JSON 格式的
演示文件，存放于 `webapp/tests/fixtures/synthetic/`。
`python3 -m demo.seed` 只向明确启用的演示数据库写入数据。
在主机生成文件需要安装项目 Python 依赖；运行 seed 还需按
[本地开发说明](docs/local-development.md)配置隔离数据库。
Docker Quick Start 已包含初始化，无需另行运行 seed。

这些名称、编码、数量和业务关系均为虚构，不是对真实业务记录进行脱敏。
演示采用四个月的计划窗口，明确区分仓库可用范围，并提供可配置的销售下降确认门槛
（`CCGTOOLS_SALES_DROP_THRESHOLD`，演示默认值为 `0.8`）。


## 技术架构与测试

前端采用原生 HTML、CSS 和 JavaScript；`webapp/main.py` 以 FastAPI 组合业务模块路由。
SQLite 保存账号与权限，SQLAlchemy / MySQL 保存 MDM、Sales 和 Ordering 的业务数据与导入记录。

Alembic 以唯一公开基线 `0001_public_baseline` 初始化业务数据库，包含关系约束和触发器。
来源版本被计划周期明确采用；预测以不可变版本保存；锁定周期保留历史及显示身份快照。
项目不包含历史销售日报模块。详细说明见[系统架构](docs/architecture.md)。

在仓库根目录运行现有测试入口：

```sh
docker compose -p ccgtools-open-demo -f deploy/local/compose.yml run --rm tests
node --test webapp/tests/public_frontend_smoke.cjs
python3 -m demo.security_scan
```

Docker 测试使用镜像内的 Python `unittest` 与项目依赖，需要先启动本地 Demo。
后两条命令需要主机安装 Python 3（提供 `python3` 命令）和支持 `node --test` 的 Node.js；
可使用 Node.js 18 或更新版本。主机安全扫描仅使用 Python 标准库。
需要项目依赖的主机开发和数据工具建议使用 Python 3.12；Docker 固定使用 Python 3.12.11。
此处主机命令使用 `python3`，无需系统提供 `python` 别名。

测试覆盖空 SQLite 账号库初始化、账号迁移与权限、MySQL 库结构及约束和触发器、
合成数据导入、销售实绩发布、预测与订货、周期锁定、登录、Portal 和前端契约。
MySQL 测试不得静默回退到 SQLite。安全扫描检查公开内容及合成工作簿元数据。

## 当前限制与未来方向

- **当前范围：** 界面以中文为主；文件适配器约定的是演示工作簿格式，不代表兼容所有 ERP。库存、来货、订货及锁定的部分操作只有服务核心，没有完整浏览器工作流。
- **人工决策：** 预测与最终订货数量由人工提供；当前公开契约采用四个月预测窗口。
- **目前不支持：** 通用 ERP API 连接、实时 ERP 同步、向来源系统自动回写或下单、通用 Semantic Layer（语义层）及自动需求预测。
- **未来方向：** 可以探索经过授权的数据接口，扩展共享实体、映射和契约的复用。这些是设计方向，不是公开版本已经实现的功能或交付承诺。
- **公开 Demo 边界：** 仅使用本机回环地址及从零生成的合成数据，不连接外部业务系统。本仓库不代表企业内部 Production 的能力或部署配置；贡献不得包含业务导出、运行数据库、日志或实际凭据。
- **HTTP 与 Cookie：** 本地 HTTP 默认不启用 Cookie Secure。使用 HTTPS 时需设置 `CCGTOOLS_PORTAL_COOKIE_SECURE=true`；HttpOnly 和 SameSite=Lax 保持启用。其他安全说明见 [SECURITY.md](SECURITY.md)。
